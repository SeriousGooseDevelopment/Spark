# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A SwiftUI port of the `Spark App.dc.html` Claude Design prototype — an ad-blocking
/ parental-controls app. Fidelity to the design is the point: colours, offsets,
icon paths and copy are transcribed rather than approximated. `README.md` records
the deliberate deviations from the `.dc.html` (mainly the Home dial) and the
behaviour added on top of the design's placeholder actions.

## Build and test

`Spark.xcodeproj` is **generated by XcodeGen and gitignored** — never hand-edit it
or `Spark/Info.plist` (also generated). Change `project.yml` instead, and re-run
`xcodegen generate` after adding, moving or deleting any source file, since the
target globs the `Spark/` directory.

`xcode-select` on this machine points at CommandLineTools, so `DEVELOPER_DIR` must
be overridden for every `xcodebuild` invocation:

```sh
xcodegen generate
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer

xcodebuild -project Spark.xcodeproj -scheme Spark \
  -destination 'generic/platform=iOS Simulator' build

# All 20 UI tests
xcodebuild test -project Spark.xcodeproj -scheme Spark \
  -destination 'id=<simulator-udid>'

# One test
xcodebuild test -project Spark.xcodeproj -scheme Spark \
  -destination 'id=<simulator-udid>' \
  -only-testing:SparkUITests/SparkFlowTests/testMasterToggleRelabelsHeroButtonAndBlockingCard
```

Device install and the `xcrun devicectl` incantations are in `README.md`.

## Architecture

**One store, no NavigationStack.** `Store` (`Spark/Store.swift`) is an
`@Observable` class created in `RootView` and injected with `.environment`;
screens read it with `@Environment(Store.self)`. It mirrors the design's
`DCLogic` object one-for-one and owns *every* mutation — navigation, modals,
lists, forms, toasts.

**`RootView` is a single z-stack**, not a `TabView`: tab content → pushed screen
→ shelf → connected pill → tab bar → quick-actions sheet → picker → form sheet →
confirm dialog → toast, at fixed `zIndex` values. Navigation is `store.stack:
[Route]` with only the topmost route rendered; the tab bar deliberately stays
above the stack. Pushed screens can nest (Help → topic → article).

**Overlays stay mounted** inside a `ZStack` whose `allowsHitTesting` is gated on
the overlay's state, rather than living inside an `if`. Wrapping them in an `if`
lets a dismissing scrim keep swallowing taps for the length of its exit
animation. Preserve this pattern when adding an overlay.

**State is string-keyed dictionaries**, matching the design: `switches[String:
Bool]` for every toggle in the app, `values[String: String]` for per-device rule
values, `apps[String: Bool]` for per-app rules, `formValues[String: String]` for
the open form. Devices use `d<N>` ids and derive their rule keys as
`"\(id)Limit"`, `"\(id)Filter"`, `"\(id)Bed"` — `submitForm`'s `.addDevice` case
must seed all three.

**Screens are data + two scaffolds.** `HeaderScreen` (Blocking/Parental/Menu) and
`PushedScreen` (device detail, generic detail) in
`Spark/Components/HeaderScreen.swift` own the indigo band and the rounded
scrolling panel. Row content is declared as arrays of small structs and rendered
through `GroupCard` / `SeparatedRows` / `SectionLabel` from `Controls.swift`.

**Detail screens are data, not views.** `DetailSpec` + `DetailRow` +
`RowAction` (`Model.swift`) describe a pushed screen; `DetailView` renders any of
them. Adding a settings-ish screen means writing a `DetailSpec` (see the statics
in `MenuView.swift` and `Content.swift`), not a new `View`.

**Forms are data too.** A form is a `FormSpec` in `Content.swift` plus a
`FormKind` case; the effect of submitting lives in `Store.submitForm`'s switch,
so all mutations stay in the store. Adding a form means touching all three.

## Design-fidelity constraints

- **Layout offsets are absolute from the top of a 402×874 display.** `RootView`
  reads the safe-area insets once, publishes them as `\.safeTop` / `\.safeBottom`,
  and the scaffolds re-anchor the design's constants to them (`safeTop + 128`
  etc.). It captures insets *once* on appear because the live reader reports the
  keyboard as a bottom inset. Root uses `.ignoresSafeArea(.container)` only, so
  SwiftUI still lifts the form sheet off the keyboard.
- **Icons are the design's inline SVG `d` strings** (`Icons.swift`), drawn by a
  real path parser (`SVGPath.swift`, supports M/L/H/V/C/S/Q/A/Z incl. elliptical
  arcs). Add glyphs as path data in the design's viewBox, not as SF Symbols or
  hand-built `Shape`s. Non-square glyphs go through `GlyphIcon`.
- **Colours and metrics live in `SK`** (`Theme.swift`) as hex literals lifted from
  the design; type goes through `SKFont`, which pulls weights off the Plus Jakarta
  Sans variable font's `wght` axis via `UIFontDescriptor`. Don't introduce ad-hoc
  `Color(...)` or `.system(size:)` calls in views.
- The app is locked to `.light` / portrait / iPhone.

## UI tests

`SparkUITests/SparkFlowTests.swift` queries **visible copy and accessibility
labels** — there are no `accessibilityIdentifier`s anywhere. Changing a string in
a screen or an `accessibilityLabel` will break tests; grep the test file before
editing copy. Controls built from `onTapGesture` need
`.accessibilityAddTraits(.isButton)` to be findable as `app.buttons[...]`.

Tests drive entry points through launch arguments, read in
`Store.applyLaunchOverrides` via `UserDefaults`: `-activeTab`, `-blockingOn`,
`-sparkConnected`, plus DEBUG-only `-openOverlay` (`sheet`/`device`/`detail`/
`picker`/`confirm`/`form`/`toast`), `-deviceID` and `-formName` for reaching
overlays that have no cold-launch path. Extend that switch when adding an overlay
that needs screenshotting.
